## Context

P10A landed a hand-rolled real-gateway bridge
(`apps/desktop/src/main/gateway/openclaw-bridge.ts`, 737 lines + 412
lines of handshake code in `openclaw-bridge-handshake.ts`) that
translates our `Router` topics into upstream OpenClaw's JSON-RPC
`req`/`res`/`event` framing — specifically the chat-only `agents.list`
+ `threads.post` happy path. P10B was scoped to align
`@openclaw/protocol` with upstream's wire shape (envelope, error format,
event taxonomy) — a multi-day churn across mobile + desktop + protocol
package.

A user-facing analysis (now committed at `.chalk/clawg-ui-evaluation.md`)
discovered that **`contextablemark/clawg-ui`** — an OpenClaw gateway
plugin pinned in this tree at `vendor/clawg-ui/` (`v0.7.0`, commit
`2498623`) — already solves the chat translation problem **server-side**:
it exposes `POST /v1/clawg-ui` as an AG-UI-compatible SSE endpoint
(`vendor/clawg-ui/src/http-handler.ts:221–348`,
`vendor/clawg-ui/README.md:39–77`), speaking the same `@ag-ui/core` /
`@ag-ui/encoder` wire format our P05C desktop adapter and our mobile
`runAgent.ts` already speak.

That means our clients can point straight at the user's openclaw daemon
for real-mode chat **without** any client-side translation layer. The
P10A bridge becomes legacy code that we tear down in P11D.

## Goal

A self-contained planning doc that, read by an engineer who hasn't
followed the chat thread, explains:

1. The decision: adopt clawg-ui for real-mode chat, retire most of
   P10A/P10B, keep stub mode for hermetic dev.
2. What changes architecturally — runtime URL, auth header, agent-id
   routing, session keying.
3. What pieces of P10A / P10B / P10C / P10D survive vs. get retired.
4. What new questions the pivot opens (pairing UX, plugin install path,
   Canvas/Voice strategy).

The doc is the "why" for the rest of Wave 15. It produces no code
changes.
