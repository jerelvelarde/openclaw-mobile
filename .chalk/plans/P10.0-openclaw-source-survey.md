# P10.0 — OpenClaw upstream protocol survey

**App:** root (research / planning doc)
**Estimated effort:** 1 day
**Depends on:** Wave 12 complete (`1727cb4`)
**Blocks:** P10A, P10B, P10C, P10D
**Can run in parallel with:** —

## Context

Waves 1–12 shipped a fully-working mobile + desktop stack against a **stub
gateway** baked into the Electron app (`apps/desktop/src/main/gateway/stub.ts`).
The stub satisfies our hand-rolled wire format (envelopes, topics, agent
events, Canvas, voice frames) but does not yet talk to the real
[`openclaw/openclaw`](https://github.com/openclaw/openclaw) gateway daemon.

Open question `#1` (the very first one we filed back in Wave 4) is still
unanswered: **what is the real OpenClaw "device node" WS protocol?**
Until we read the upstream source and pin that contract, we can't claim our
desktop app actually supervises OpenClaw — it ships a parallel implementation.

This plan is the research spike that unblocks P10A–D.

## Goal

A written, accurate spec of the real OpenClaw gateway's external contract,
captured in `.chalk/openclaw-upstream.md`. Concretely:

- Daemon lifecycle (install, start, stop, log location, supervision hooks).
- Filesystem layout (`~/.openclaw/workspace/`, skills, channels, settings).
- HTTP surface (port, paths, auth, healthz, pairing, agent list, channels list).
- WS surface (URL, auth, message envelope, topic taxonomy, heartbeats, error frames).
- Agent lifecycle (how skills are loaded, how `AGENTS.md` / `SOUL.md` / `TOOLS.md` interact, how the multi-agent router selects).
- Hermes interop (`hermes claw migrate` — what does it actually change in `~/.openclaw/workspace/`?).
- Canvas + voice — do these exist upstream, or are they our additions?
- What gaps exist between upstream and our protocol package, with concrete deltas.

## Inputs

- `https://github.com/openclaw/openclaw` (read-only clone, or read via WebFetch).
- `https://github.com/NousResearch/hermes-agent` (for the migrate semantics).
- Our own `packages/protocol/src/` as the comparison baseline.

## Outputs

- **`.chalk/openclaw-upstream.md`** — the spec doc. ~300–500 lines. Source-of-truth references with file paths + line numbers from the upstream repos.
- **`.chalk/openclaw-deltas.md`** — gap analysis: what `@openclaw/protocol` agrees with upstream, what diverges, and the cost/benefit of each divergence.
- Updates to `.chalk/open-questions.md`:
  - Mark `#1` (WS protocol) **resolved** with the spec doc as the resolution.
  - Mark `#2` (`openclaw-desktop` repo ownership) **discussed** — note any upstream comments about external supervisors.
  - Mark `#10` (Hermes wiring) **clarified** with what `hermes claw migrate` actually does.
  - Add new questions for any deltas that need decisions.
- A short PR-back list in `.chalk/openclaw-upstream.md` final section: things our work might be worth contributing upstream (Canvas schema, Voice protocol, CopilotKit runtime adapter).

## Steps

1. **Clone or fetch the upstream repos** into `/tmp` (do **not** add submodules here).
   ```sh
   git clone --depth=1 https://github.com/openclaw/openclaw /tmp/upstream-openclaw
   git clone --depth=1 https://github.com/NousResearch/hermes-agent /tmp/upstream-hermes
   ```
   If the clones fail due to network policy, use WebFetch against the GitHub UI URLs and proceed best-effort with whatever excerpts you can read.
2. **Survey the gateway daemon.** Identify (with file + line refs):
   - Entry point (`openclaw gateway` CLI handler).
   - HTTP server framework + bound port (default `18789` per the README — confirm).
   - Route table for pairing, healthz, agent list, channel hooks.
   - WS upgrade handler, auth check, frame envelope shape.
   - Topic taxonomy or equivalent (subscriptions, routing keys, etc.).
3. **Survey the agent execution model.**
   - How skills under `~/.openclaw/workspace/skills/<skill>/` are loaded.
   - What `AGENTS.md` / `SOUL.md` / `TOOLS.md` actually become at runtime (system prompts? function bindings?).
   - How the multi-agent router selects which agent responds to which message.
   - The agent ↔ gateway IPC (in-process JS calls? child-process JSON? WebSocket back-channel?).
4. **Survey Hermes interop.**
   - `hermes claw migrate` — what files it writes, what config it expects.
   - Does Hermes run as a sibling process, an OpenClaw skill plugin, or something else?
5. **Compare with `packages/protocol`.** For each upstream concept, note whether our shape matches, can be adapted, or conflicts:
   - Envelope: `{ id, topic, type, payload, ts }` (ours) vs upstream.
   - Topics: `threads.*`, `agents.*`, `canvas.*`, `voice.*`, `system.*` (ours) vs upstream's topic taxonomy.
   - Tokens: Ed25519 signed JWT-like (ours) vs upstream's auth.
   - Pairing handshake (ours): `POST /pair/request` + 6-digit code + `GET /pair/status` polling. Compare upstream.
   - Canvas + voice — confirm absent or present upstream.
6. **Write `.chalk/openclaw-upstream.md`** with the spec, source refs, and a "v1 mapping cheat sheet" so P10A's bridge implementation can reference exact upstream call sites.
7. **Write `.chalk/openclaw-deltas.md`** with the gap analysis (table format).
8. **Update `.chalk/open-questions.md`** as described under Outputs.
9. **Do not change any code in `apps/` or `packages/`** in this plan. Documentation only. The deltas might suggest large changes to `@openclaw/protocol`; those land in P10B.
